# 1. Análise de Práticas Ágeis no Processo

| Prática | Existe no processo? | Como é aplicada atualmente? | Pode ser melhorada? |
|----------|----------|----------|----------|
| Planejamento iterativo | Parcial | As tarefas vão sendo divididas em partes menores conforme a necessidade, mas não existe um ciclo fixo de planejamento | Sim, definindo ciclos curtos tipo sprints |
| Priorização de funcionalidades | Sim | A prioridade é decidida pelo que está travando mais o desenvolvimento ou pelo que é exigido na disciplina, sem um critério formal | Sim, montando um backlog com prioridades definidas |
| Entregas incrementais | Sim | Cada funcionalidade é entregue separada, conforme vai ficando pronta | Sim, padronizando um tamanho mais regular pros incrementos |
| Feedback frequente | Parcial | O feedback acontece principalmente nas correções de aula. | Sim, buscando feedback com mais frequência. |
| Trabalho colaborativo | Não | Como o trabalho é individual, não existe colaboração direta com outra pessoa durante o desenvolvimento | Sim, buscando alguém pra revisar ou compartilhar duvidas sobre o código |
| Controle visual das atividades | Parcial | As tarefas ficam anotadas em lista, mas não tem um quadro visual organizado | Sim, montando um kanban simples pra acompanhar o andamento |
| Melhoria contínua | Não | Não existe um momento certo pra parar e pensar no que pode melhorar, os ajustes só acontecem quando aparece algum problema | Sim, criando retrospectivas pessoais ao final de cada etapa |

### Conclusão

O processo conta com algumas práticas ágeis presentes, mas de forma bem informal. As entregas são feitas em partes e a prioridade é definida pelo que trava mais o andamento, porém não existe um ciclo fixo de planejamento nem um quadro visual organizado das tarefas. Como o trabalho é individual, não tem colaboração direta com outra pessoa, e isso acaba deixando o feedback escasso, ficando concentrado principalmente nas correções de aula. O ponto mais fraco é a melhoria contínua, já que os ajustes no processo só acontecem quando algum problema aparece, não existe um momento reservado pra refletir sobre o que pode ser melhorado. Definir ciclos mais curtos, montar um quadro de tarefas e reservar um momento de retrospectiva, mesmo sendo um trabalho individual, ajudaria a deixar o processo mais ágil.

# 2. Propostas de Melhoria Ágil

| Melhoria Proposta | Metodologia Relacionada | Benefício Esperado |
|------------------|------------------------|--------------------|
| Definir sprints curtos para organizar as tarefas | Scrum | Mais previsibilidade nas entregas |
| Criar um quadro kanban para acompanhar o andamento das tarefas | Kanban | Visualizar melhor o que está em andamento e o que falta |
| Montar um backlog com prioridades definidas | Scrum | Foco no que é mais importante em cada entrega |
| Fazer retrospectivas pessoais ao final de cada etapa | Scrum | Identificar o que pode melhorar no processo |

# 3. Definition of Ready (DoR)

Uma funcionalidade estará pronta para desenvolvimento quando:

1. O requisito estiver claro e entendido.
2. Os critérios de teste já estiverem definidos.
3. Não existir dependência de outra tarefa que ainda está em andamento.
4. Estiver definido onde a funcionalidade vai impactar no sistema.
5. Tiver tempo disponível pra implementar sem atrapalhar o desenvolvimento de outra tarefa.

---

# 4. Definition of Done (DoD)

Uma funcionalidade será considerada concluída quando:

1. O código estiver pronto e funcionando.
2. Os testes tiverem sido executados e passado.
3. Não existir nenhum defeito conhecido pendente.
4. A funcionalidade estiver publicada no ambiente.
5. A documentação, quando necessária, estiver atualizada.
